# サッカー戦術シミュレーションゲーム — 開発引き継ぎ資料

Cowork上でのClaude(このAI)とのやり取りを通じて開発したサッカー戦術シミュレーションです。
Claude Codeで開発を引き継ぐために、コード一式・仕様・検証結果・既知の課題をこのリポジトリにまとめています。
**開発の目的**: サッカー戦術の分析（得意・不得意な相手の戦術、勝率を上げる工夫、典型的なパスコースの洗い出し）。
特にデゼルビ(Roberto De Zerbi)のポゼッション戦術の再現を目標としている。
Claude Code向けの開発ガイド・規約は `CLAUDE.md` を参照。

## 1. 実行方法

Python 3系（標準ライブラリのみで動作、追加パッケージ不要）。
リポジトリのルートで実行する（Windowsは `python`、macOS/Linuxは `python3`）。

```bash
# 45分ハーフ(2700ステップ)を1試合フル実行し、CSVとサマリーを出力
python run_match.py

# 10試合連続実行し、戦術別成績等の集計を1ファイルに出力
python run_10_matches.py

# 10試合を実行し、試合ごとに個別のCSV/サマリーを出力(末尾に1〜10)
python run_10_matches_separate.py

# 短時間(デフォルト36ステップ=36秒)だけ動かして動作確認したい場合
python run_preview.py
python run_preview.py 30   # ステップ数を指定
```

`run_match.py`を実行すると、このフォルダに以下が生成されます。
- `match_full_half.csv` — 全ステップ・全選手のログ
- `match_result.txt` — サマリー（イベント件数、ゴールログ、7地点のアスキー図スナップショット）

生成された`match_full_half.csv`は、同梱の`match_playback.html`をブラウザで開いて
ドラッグ&ドロップすると、選手・ボールの動きをコマ送り再生できます（ネット接続不要）。

## 2. ファイル構成

| ファイル | 役割 |
|---|---|
| `players.py` | 選手データ定義。フォーメーション(4-4-2/4-3-3/3-5-2)ごとの11人・能力合計1000点の配分、キックオフ配置、背番号 |
| `formation.py` | フォーメーションごとの攻撃時/守備時のデフォルトポジション、戦術(line_height/width)反映、ボール位置に応じた追随ロジック |
| `ball_logic.py` | パス選択・成功判定、インターセプト判定、シュート・着弾列判定・ゴール判定 |
| `tactics.py` | チーム戦術プリセット(5パターン、フォーメーション+4軸: line_height/width/pass_risk/press_intensity) |
| `engine.py` | メインエンジン(`MatchSim`クラス)。1秒ごとの状態更新、戦術抽選、CSV出力、アスキー図生成 |
| `run_match.py` | 45分ハーフ(2700ステップ)本実行スクリプト(1試合、`match_result.txt`/`match_full_half.csv`を出力) |
| `run_10_matches.py` | 45分ハーフを10試合連続実行し、戦術別成績等を`match_10games_result.txt`に出力(集計1ファイル) |
| `run_10_matches_separate.py` | 45分ハーフを10試合実行し、試合ごとに`match_result_<N>.txt`/`match_full_half_<N>.csv`(N=1〜10)を個別出力 |
| `run_preview.py` | 短時間プレビュー用スクリプト(動作確認・改造時に使用) |
| `match_playback.html` | 試合再生ビューア。ブラウザで開いてCSVを読み込むとコマ送り再生できる(単一ファイル・依存なし) |
| `CLAUDE.md` | Claude Code向けの開発ガイド(実行・検証手順、変更時の規約、バックログ) |

依存関係: `run_match.py` / `run_preview.py` → `engine.py` → `players.py` / `formation.py` / `ball_logic.py` / `tactics.py`

## 3. 仕様概要

- コート: 縦105マス × 横65マス（1マス=1m換算）
- 座標: `(row, col)`。row=1が自陣(Aチーム基準)、row=105が敵陣。Bチームはミラー配置。
- 時間: 1秒刻み、45分ハーフ = 2700ステップ（`engine.TOTAL_STEPS_PER_HALF`）。
  ただしボールアクション(パス/シュート判定)自体は毎秒ではなく平均3秒に1回の頻度で発生させている
  （`engine.ACTION_PROB_PER_STEP`）。毎秒判定すると同じ実時間でのターンオーバー確率が
  3倍の頻度で累積してしまい試合が成立しなくなるため、位置更新は毎秒・意思決定は3秒に1回、という形で分離している。
- 選手能力: 5項目(キック力・スピード・正確性・視野・戦術理解)、チーム合計1000点をポジション別に配分
- 移動: 選手のspeed能力に応じて1秒あたり最大1〜5マス(m)移動(`engine.max_cells_for`)
- 体力ゲージ: **現行仕様では無効化**（純粋戦術検証のため、体力による速度・能力低下は実装していない）
- チーム戦術: `tactics.py`に定義した5プリセットから、各チームが試合開始時に自動でランダム選択する
  (`MatchSim.__init__`)。プリセットは「フォーメーション(4-4-2/4-3-3/3-5-2)」と4軸
  (line_height=守備ラインの高さ、width=横の広がり、pass_risk=パスのリスク許容度、
  press_intensity=プレスの強度)を持ち、フォーメーションは`players.build_team`で選手構成・能力配分に、
  line_height/widthは`formation.get_default`でポジショニングに、
  pass_risk/press_intensityは`ball_logic`のパス選択・インターセプト判定・シュート積極性に反映される。
  現状は「ハイプレス」に4-3-3(アンカー+インサイドハーフ2枚、ワイドな3トップ)、
  「リトリート堅守」に3-5-2(3バック+ウイングバック2枚+中盤3枚、2トップ)を割り当て、
  残り3プリセットは4-4-2のまま(`players.FORMATIONS` / `formation.FORMATION_TABLES`)。
  さらに`false_nine`(偽9番: 攻撃時にFW1が中盤へ降り、MF_CM1が入れ替わりで前線へ)と
  `fb_role`(SBの攻撃時役割: "overlap"=高く外へ張り出す / "inverted"=内側ハーフスペースへ
  絞る偽SB / "normal")のフラグを持つ。現状「ポゼッション安全策」がfalse_nine+inverted
  (デゼルビ/ペップ式)、「サイド攻撃」がoverlap(アウベス型)を採用。
- ゾーン(3レーン理論): 列位置を「中央(|col-33|<8) / ハーフスペース(8〜18) / サイド(19以上)」に
  分類(`ball_logic.col_zone`)。敵陣ハーフスペースに立つ味方へのパスにボーナスを与え、
  ポジショナルプレーの「ハーフスペース支配」を再現する。スルーパスの典型レーンでもある。
- ポジショニング: 各選手はポジション・フォーメーションごとの「攻撃時デフォルト位置」
  「守備時デフォルト位置」(戦術補正込み)を持ち、ボールのrow/col位置に応じて追随する
  (`formation.dynamic_target`)
- パス: 視野に応じた射程内から前進度・距離・戦術のpass_riskでスコアリングし、上位候補から重み付きランダム選択。
  サイドの選手(FB/ワイドMF)へは戦術のwidthに応じたボーナスが加わり、width重視の戦術ほど
  サイド展開を選びやすくなる。
- インターセプト: 最寄りの守備者との距離・戦術理解値・相手チームのpress_intensityから確率算定
- クロス: ボール保持者がサイド(コート中央から19マス以上)かつアタッキングサード内
  (相手ゴールから35m以内 = `ball_logic.CROSS_ZONE_DEPTH`)にいる場合、シュートの代わりに
  クロスを試みる。ボックス内(中央±19マス・相手ゴールから30m以内)に走り込んでいる味方を探し、
  いれば成功率判定(成功=`CROSS_OK`でその味方にボールが渡る、失敗/インターセプトで攻守交代)。
  ボックス内に味方がいなければ通常のパス選択にフォールバックする。
- シュート/ゴール: ボール保持者が中央寄りでシュートゾーン(相手ゴールから20m以内)に入ると
  一定確率でシュートを試みる。まず選手の正確性と乱数から「着弾列(col)」を算出し、
  ゴールエリア(コート横中央から左右3マス、計7m幅 = `ball_logic.GOAL_ZONE_HALF_WIDTH`)の
  範囲外なら自動的に枠外(`SHOT_OFF_TARGET`)。範囲内ならキック力・正確性とGKの能力・距離から
  成功率を算定し、成功でゴール成立、失敗ならGKがセーブ(`SHOT_SAVED`)。
  ゴール成立でスコア加算、キックオフに戻る(戦術は維持)。
- カットバック: シュートゾーン内でボールを持った際、シュートの前に一定確率でボックス内へ
  走り込んでいる味方(MFを`CUTBACK_MF_BONUS`で優先)への折り返しを検討する。対象がいれば
  成功率判定(成功=`CUTBACK_OK`)、いなければ通常通りシュートを試みる。
- ミドルシュート: MFがシュートゾーンには届かないがアタッキングサード内(相手ゴールから40m以内)
  にいる場合、低確率・低成功率(上限0.30)でロングシュートを試みる。着弾列・ゴールエリア判定の
  仕組みは通常のシュートと共通だが、着弾のブレが大きく成功率も低めに設定している。
  いずれもFW以外の得点パターンを増やすための経路(`ball_logic.py`)。
- バックパス: DFがボールを持った際、一定確率(戦術のpass_risk/line_heightで補正)でGKへ戻す
  ビルドアップを検討する。成功=`BACKPASS_OK`でGKにボールが渡る、失敗/インターセプトで攻守交代。
- GKビルドアップ配球: GKがボールを持ったときは前進度ではなく「フリー度」(受け手の最寄りの
  相手までの距離)で配球先(CB/SB/アンカー/WB)を選ぶ(`choose_gk_distribution`)。相手プレスが
  片側に寄れば逆の空いた方へ散らされる(デゼルビの「引きつけてから逃がす」ビルドアップ)。
  成功=`BUILDUP_OK`。フリーな受け手が対象のため成功率に上方補正あり。
- サイドチェンジ(「2進んで1戻る」): 同じサイドで前進できないアクションが2回続くと、
  逆サイドの受け手へのパスにボーナスが付き、相手ブロックを左右に揺さぶる
  (`SWITCH_AFTER_STUCK`/`SWITCH_BONUS`、状態は`sim._side_state`)。
- スルーパス(裏抜けラン): 敵陣に入った保持者が、最終ラインの手前で駆け引きしているFWの
  裏のスペースへパスを通す。成功=`THROUGH_OK`で受け手がライン裏へ実際に走り込んだ状態で
  ボールを持ち、一気にシュートチャンスになる。ハーフスペース経由にボーナス。
  飛び出しが早すぎるとオフサイド(`THROUGH_MISTIME_PROB`)。
- オフサイド: パスの瞬間の受け手が「敵陣内」「最終ライン(守備側で2番目にゴールに近い選手)
  より3m超前」「ボールより前」をすべて満たすと`OFFSIDE`。通常パス/クロス/カットバック/
  スルーパスに適用され、相手ボール(最寄りの守備者のFK相当)で再開する。攻撃側の保持者以外の
  選手はオフサイドラインの手前で止まって駆け引きする(engine側でターゲット位置をクランプ)。
  これによりハイラインは「裏を取られるリスク」と「相手をオフサイドにかける武器」の
  トレードオフを持つ。
- GKの飛び出し: クロスの送り先が決まった後、守備側GKが飛び出してキャッチできるか判定する
  (`GK_CLAIM`)。GKからの距離・GKの正確性・守備側の戦術(press_intensity/line_height)を反映。
  失敗した場合は通常のクロス解決(インターセプト→成功/失敗判定)にフォールバックする。

## 4. 開発の経緯（検証の流れ）

1. 初期仕様（縦20×横15マス、6秒刻み・450分割、体力ゲージあり）でプロトタイプを作成し、
   パスロジック・ボールロストロジックが未定義であることなど複数の設計上の穴を洗い出した。
2. ユーザー指示により、時間間隔を3秒・900分割に変更、1ステップ最大3マス移動、
   パス/ボールロストロジックを実装、体力ロジックを削除、デフォルト攻撃/守備位置を導入。
3. ボール保持者交代直後に前保持者が慣性で不自然に飛び出す不具合を修正
   （ボールアクション解決→新保持者確定→全員のポジション更新、の順序に変更）。
4. パス候補が同じ相手に固定されやすく、特定選手間でボールが往復し続ける「膠着」現象が発生。
   パス候補選択にランダム性・連続パスへのペナルティ・DF間パスへのペナルティ・
   MF/FWへの前進ボーナスを追加し、インターセプト確率の上限を下げることで解消を確認。
5. 900ステップ(45分)のフル実行に対応させ、シュート・ゴール判定を新規追加した上で
   通し実行を検証（実行時間0.27秒、CSV行数19,801行で期待値と一致、座標範囲外なし、
   13ゴール発生でスコアA8-B5という結果を確認）。
6. ユーザー指示により、コートを1マス=1m単位(縦105×横65マス)、時間を1秒刻み(2700分割)、
   1秒あたり最大移動5m(能力に応じて1〜5マス変動)、ゴールエリア(横中央±3マス=7m幅)を
   ボールが通過した場合のみゴール判定、という4点を変更。
   あわせてチーム戦術プリセット(5パターン、line_height/width/pass_risk/press_intensityの4軸)を
   `tactics.py`に新設し、各チームが試合開始時に自動抽選するようにした。
7. コート変更後の初回フル実行検証で、45分間シュートが一度も発生しない不具合を発見。
   原因は2点: (a) ボールアクション(パス/インターセプト判定)を毎秒(1秒刻み)行うと、
   旧仕様(3秒刻み)に比べ同じ実時間でのターンオーバー確率が3倍の頻度で累積してしまう、
   (b) ボール保持者の前進ボーナス(旧仕様で2マス≒10m相当)が新グリッドでも「2マス=2m」のまま
   スケール換算されておらず、シュートゾーン手前で頭打ちになっていた。
   前者はボールアクションの意思決定頻度を平均3秒に1回に維持する形で、
   後者は他の距離定数と同じ換算係数(SCALE=5)でメートル換算する形で解消し、
   45分フル実行でゴール発生・ゴールエリア判定(着弾列30〜36列に限定)を確認した。
8. match_full_half.csvをパラパラ漫画的に再生できるHTMLビューア(Artifact)を作成。
   CSVをブラウザ上で読み込み、選手・ボールの位置をコマ送り再生する。
9. 生成したCSVを分析した結果、(a) イベント(ゴール等)がアクション実行後の新しい
   ボール保持者の行に記録されており、ゴール発生時は失点側チームの行に記録される
   バグを発見・修正(`engine.py`でアクション実行前の保持者を保存してから記録する形に変更)。
   (b) 「サイド攻撃」戦術(width重視)が構造的に得点機会に繋がっていないことも判明
   (シュートゾーン侵入判定が中央の縦深さのみに依存し、サイドの選手がボールを持っても
   FWのように深い位置まで押し上げられないため)。
10. 9(b)への対応として、サイドの深い位置(アタッキングサード内)にいるボール保持者は
    シュートではなくクロスを試みるロジックを追加(`ball_logic.py`: `CROSS_ZONE_DEPTH`
    `choose_cross_target` `cross_success_probability`等)。ボックス内(中央±19マス・
    深さ30マス)に走り込んでいる味方を探して成功判定する。
    あわせて`choose_pass_target`に戦術のwidthに応じたサイド展開ボーナスを追加し、
    サイドの選手が実際にボールを引き出しやすくした。導入時、受け手側の
    「ボックス」判定がシュートゾーンと同じ深さ(20マス)だったためFWがそこまで
    上がってこられず終始不成立だったことが判明し、判定の深さを30マスに緩めて解消。
    複数シードで検証し、CROSS_OK/CROSS_FAILイベントが安定して発生することを確認した。
11. 「得点がFWに偏る」既知課題への対応として、2つの得点経路を追加。
    (a) カットバック: シュートゾーン内でボールを持った際、シュートの前にボックス内へ
    走り込んでいる味方(MF優先)への折り返しを検討する(`choose_cutback_target`)。
    (b) ミドルシュート: シュートゾーンには届かないがアタッキングサード内(40m以内)にいるMFが、
    低確率・低成功率(上限0.30)でロングシュートを試みる(`in_mid_shoot_zone`
    `mid_shot_success_probability`)。20試合の集計で、改修前は100%FWだった得点者が
    MF_CM1/CM2合計で約14.6%まで多様化したことを確認した。
12. 「GKの関与を増やす」既知課題への対応として、2つの機構を追加。
    (a) バックパス: DFがボールを持った際、一定確率でGKへ戻すことを検討する
    (`backpass_try_probability`)。通常のパススコアリングは前進度重視でGKが実質選ばれないため、
    独立した分岐として実装。確率は戦術のpass_risk(低いほど戻しやすい)とline_height
    (低い＝リトリートほど戻しやすい)で補正される。
    (b) GKの飛び出し(クロスキャッチ): クロスの送り先が決まった後、通常のインターセプト判定の前に
    守備側GKが飛び出してキャッチできるか判定する(`gk_claim_probability`)。GKからクロス着弾点
    までの距離、GK自身の正確性、守備側チームのpress_intensity/line_height(高いほど積極的に
    飛び出す)を反映。失敗時は通常のクロス解決にそのままフォールバックする(合意通りのシンプル実装)。
    検証の結果、リトリート堅守とハイプレスでバックパス頻度に約20倍の差(1試合平均1.55回 vs 30.1回)
    が出ることを確認し、守備側の戦術差が明確に表れるようになった。GK飛び出しは関数単体では
    戦術による確率差(15m地点でリトリート0%・バランス3.2%・ハイプレス19.6%)を確認できたが、
    実戦ではクロスの着弾点がGKの守備範囲より遠いことが多く、発生頻度自体は稀。
13. 「フォーメーション自体の戦術差」既知課題への対応として、4-3-3を追加。
    `players.py`/`formation.py`をフォーメーションごとのテーブル(`FORMATIONS`/`FORMATION_TABLES`)に
    再構成し、`tactics.py`の各プリセットに`formation`キーを追加。今回は「ハイプレス」にのみ
    4-3-3(アンカー+インサイドハーフ2枚、ワイドな3トップ)を割り当て、他は4-4-2のまま据え置いた
    (段階導入の方針)。`ball_logic.py`の`WIDE_POS_KEYS`(列挙型)は`WIDE_POS_SUFFIXES`
    (サフィックス判定)に一般化し、新しいポジションキー(FW_LW/FW_RWなど)を個別に列挙しなくても
    自動的にサイド判定されるようにした。複数シードで検証し、フォーメーション抽選比率(5プリセット中
    1つ=約20%)・座標範囲・CSV整合性が正しいことを確認。ウイング(FW_LW/RW)は既存のクロス機構により
    自らはあまりシュートせず供給役に回る(現実のウイングの役割に近い)ことも確認した。
14. 続けて3-5-2を追加し、「リトリート堅守」に割り当てた。3バック(DF_CB1〜3)+
    ウイングバック2枚(MF_LWB/RWB)+アンカー(MF_DM)+インサイドハーフ2枚(MF_CM1/CM2)+2トップの構成。
    ウイングバックは`LINE_HEIGHT_SENSITIVITY`を高め(0.9)に設定し、守備時は5バック的に絞り、
    攻撃時はライン全体の押し上げに連動して高い位置まで駆け上がるようにした。
    4-3-3導入時に一般化しておいた`WIDE_POS_SUFFIXES`のおかげで、`ball_logic.py`側の追加変更は
    不要だった(LWB/RWBサフィックスは導入済み)。40試合の集計でフォーメーション抽選比率
    (4-4-2 61%・4-3-3 19%・3-5-2 20%、理論値60%/20%/20%とほぼ一致)・座標範囲・
    CSV整合性を確認した。
15. 10試合を連続実行するスクリプト`run_10_matches.py`を新規作成し、`match_10games_result.txt`に
    別ファイルとして出力するようにした(既存の`match_result.txt`/`match_full_half.csv`は上書きしない)。
    実行したところ、リトリート堅守(3-5-2)が10試合0勝10敗(得点5-失点42)という
    偏った結果になっていることが判明。診断の結果、パラメータ以前に2つのフォーメーション設計の
    不具合が主因と判明した。
    (a) 3-5-2のFW1/FW2の基準列が中央から離れすぎており(新グリッド換算後で列24・42、
    ゴールエリアは列30〜36)、シュートの84.6%が枠外になっていた。FW1/FW2の間隔を
    4-4-2と同じ(中央±1マス相当)に詰めて解消。
    (b) ウイングバック(MF_LWB/RWB)の`LINE_HEIGHT_SENSITIVITY`が0.9と高すぎたため、
    リトリート堅守の`line_height=-8`と組み合わさると攻撃時も深く引き戻されすぎ、
    クロスゾーン(相手ゴールから35m以内)に一度も到達できずクロス成功が0本だった。
    感度を0.35に下げ、ライン高さより「攻撃/守備フェーズ」と「ボール追随」で
    ポジションが決まる比重を大きくして解消。
    その上でline_height(-8→-4)・width(0.9→1.0)・pass_risk(0.8→1.0)・
    press_intensity(0.8→1.2)も調整し、全プリセット総当たり32試合で7勝5分20敗(勝率22%、
    改修前は事実上0%)まで改善したことを確認した。それでも依然として得点の伸びにくい
    プリセットではあり、さらなる調整の余地がある。
16. デゼルビ/ポジショナルプレー系の戦術再現を目的に、6つの機構をまとめて追加。
    (1) ハーフスペースの3レーン分類とパスボーナス、(2) GK保持時のフリー度基準の
    ビルドアップ配球(BUILDUP_OK/FAIL)、(3) 同サイドで詰まったら逆サイドへ展開する
    「2進んで1戻る」サイドチェンジボーナス、(4) 偽9番フラグ(攻撃時にFW1↓・MF_CM1↑の
    入れ替わり、ポゼッション安全策に適用)、(5) SBの役割フラグfb_role(overlap=アウベス型/
    inverted=偽SB、サイド攻撃とポゼッション安全策に適用)、(6) スルーパス(裏抜けラン、
    THROUGH_OK/FAIL)とオフサイド判定(OFFSIDE)のセット導入。
    (6)では導入直後にオフサイドが約200回/試合と非現実的な頻度で発生する問題が出た。
    原因はFWの基準位置が相手最終ラインを恒常的に越えていたことで、(a) 攻撃側の保持者以外は
    オフサイドラインの手前で止まる動き(engine側のターゲットクランプ)、(b) ラインの上下動への
    追随ラグを吸収する3mの許容幅(ONSIDE_TOLERANCE)の2段構えで約15回/試合まで正常化した。
    ハイライン(ハイプレス)がローライン(リトリート堅守)より相手のオフサイドを多く誘発する
    トレードオフ(5.1回 vs 4.3回/試合)も確認。30試合のバランス確認ではハイプレスが最強
    (10勝2敗)だが他は拮抗しており、試合が壊れていないことを確認した。

## 5. 既知の課題・改善余地（Claude Codeでの開発時に検討してほしい点）

- **シュート成功率が高止まりしやすい**: `ball_logic.shoot_success_probability`の
  `base`計算がやや大きく、上限0.6に張り付きやすい。GKの反応や距離の影響をもっと強めたい。
- **得点がFW(背番号10・11)に偏る**: カットバック・ミドルシュートの追加でMFの得点比率は
  改善した(20試合集計でMF合計約14.6%)が、依然FWが大半を占める。DFの得点(セットプレー由来)は
  コーナーキック等が未実装のため対象外。さらに比率を変えたい場合は`CUTBACK_MF_BONUS`や
  `MID_SHOT_TRY_PROB`を調整する。
- **フォーメーションは4-4-2/4-3-3/3-5-2の3種類、割り当ては1プリセットずつのみ**:
  「サイド攻撃」「ポゼッション安全策」「バランス型」は4-4-2のまま。他のフォーメーション
  (例: 4-2-3-1等)を追加する場合は`players.FORMATIONS`/`formation.FORMATION_TABLES`に
  新規エントリを追加し、`tactics.py`の該当プリセットに`"formation"`キーを設定すればよい
  (設計・実装パターンは4-3-3/3-5-2導入時と同様)。ポジションキーの先頭を"DF_"/"MF_"/"FW_"/"GK"に、
  サイドのポジションは末尾サフィックスを`ball_logic.WIDE_POS_SUFFIXES`に含める規約さえ守れば、
  既存ロジック側の追加変更は基本的に不要。
- **距離系の定数のメートル換算(`SCALE`/`GRID_SCALE`)はヒューリスティックな近似**:
  `ball_logic.py`のSCALE=5、`engine.py`のGRID_SCALE=5は「旧グリッド1マス≒5m」という
  ざっくりした換算で全定数を一律スケールしたもの。プレースタイルの統計を見ながら
  個別に微調整する余地がある。
- **体力ゲージは仕様として削除済み**: 将来的に「体力を戦術に影響させたい」場合は
  `players.py`の`stamina`フィールド（現状未使用で残置）を使って再実装できる。
- **ファウル・スローイン・コーナーキックなどは未実装**: オフサイドは実装済みだが、
  その他のセットプレーは未対応。オフサイドの発生頻度(約15回/試合)は実際の試合(2〜6回)より
  やや多め。さらに減らしたい場合は`ONSIDE_TOLERANCE`を広げるか`THROUGH_MISTIME_PROB`を下げる。
- **戦術バランスはハイプレスが最強**: 6機構導入後の30試合確認でハイプレス(4-3-3)が10勝2敗と
  突出。「ポゼッション安全策」は偽9番+偽SBを持つが勝率が伸びておらず(pass_risk=0.7で
  シュート試行自体が少ないため)、チューニングの余地がある。
- **この開発環境（Cowork）特有の注意点**: 作業中、既存ファイルをEditツールで部分編集すると
  ファイル末尾が欠損する不具合が複数回発生した（原因はファイルシステム同期の問題と推測）。
  Claude Codeの通常の開発環境ではこの問題は再現しない可能性が高いが、
  ファイル編集後は必ず実行して動作確認する習慣を推奨する。

## 6. 出力ファイルと可視化

実行スクリプトが生成するファイル（`.gitignore`でリポジトリからは除外。手元で再生成すること）:
- `match_full_half.csv` / `match_result.txt`: `run_match.py`の1試合分の出力
- `match_10games_result.txt`: `run_10_matches.py`の10試合集計
- `match_full_half_<N>.csv` / `match_result_<N>.txt` (N=1〜10): `run_10_matches_separate.py`の個別出力

可視化: `match_playback.html`（リポジトリ同梱・単一ファイル・ネット接続不要）をブラウザで開き、
CSVをドラッグ&ドロップすると45分間をコマ送り再生できる。再生/一時停止・コマ送り・
スクラブ・速度切替(1×〜30×)・スコア/イベント表示に対応。
（開発時のオリジナルはClaude Artifact: https://claude.ai/code/artifact/5190a711-a165-43cc-9545-18b663b02ef5 ）

## 7. 元の要件（ユーザー指示の要約）

1. サッカーコートを縦20×横15のマス目に分割
2. 両チームのプレーヤーをそのマス目上に配置
3. 45分ハーフを6秒ごと(のちに3秒ごとに変更)に分割し、各場面のプレーヤー配置をプロット。
   チームごとに事前定義した攻撃・守備戦術に従いポジション変化やボール運びを決定し、次の時間につなげる
4. 各プレーヤーは前回時間帯からの移動速度(m/秒)と方向を算定
5. 11名の合計能力は1000点、任意配分。能力が高いほどキック力・スピード・正確性・視野・戦術理解が比例
6. 体力ゲージ(試合前100、50未満で速度・能力25%低下、25未満で50%低下) → **のちにユーザー指示で無効化**
7. 各時間帯のデータをCSVに保存(時間ごとに追加)
8. チャット画面に結果表示: プレーヤー配置のテキスト表、テキストベースのアスキー図
   (背番号1-11、Aチーム/Bチームで A01, B01のように表示)

3, 6は開発途中でユーザー指示により変更（3: 6秒→3秒・450→900分割、1ステップ最大3マス移動、
パス/ボールロストロジック追加。6: 体力ゲージ無効化）。

その後さらにユーザー指示により以下を追加変更（詳細は「4. 開発の経緯」6・7参照）。
- コートを1マス=1m単位(縦105×横65マス)、時間を1秒刻み(2700分割)、
  1秒あたり最大移動5m(能力に応じて変動)に変更
- ゴールエリア(横中央から左右3マス=計7m幅)をボールが通過した場合のみゴール判定とするよう変更
- チーム戦術プリセット(5パターン、line_height/width/pass_risk/press_intensityの4軸)を新設し、
  各チームが試合開始時に自動抽選するように変更
